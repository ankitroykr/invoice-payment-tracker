# Invoice and Payment Tracker

[![CI](https://github.com/ankitroykr/invoice-payment-tracker/actions/workflows/ci.yml/badge.svg)](https://github.com/ankitroykr/invoice-payment-tracker/actions/workflows/ci.yml) [![Licence](https://img.shields.io/github/license/ankitroykr/invoice-payment-tracker)](LICENSE) [![.NET 10](https://img.shields.io/badge/.NET-10.0-512BD4)](https://dotnet.microsoft.com/download/dotnet/10.0)

A personal project to build an invoice and payment tracker from scratch, the way I would at work: in small pull requests, with CI checking every change.

When complete, the application will let freelancers create invoices, record full and partial payments, and keep track of outstanding and overdue balances. It is built with ASP.NET Core and SQL Server and hosted on Azure, with an Angular front end planned.

## Technology stack

- **Backend:** C#, ASP.NET Core (.NET 10)
- **Architecture:** Clean Architecture with a rich domain model (Domain, Application, Infrastructure and API layers)
- **Validation:** FluentValidation, run by each use case in the Application layer
- **Data:** SQL Server 2022 (Docker locally) with Entity Framework Core 10
- **Caching:** HybridCache, in memory, for reference data such as the supported currencies
- **Security:** OAuth 2.0 access tokens from Microsoft Entra ID, validated with ASP.NET Core's JwtBearer handler, and app roles checked through named authorization policies
- **Logging:** Serilog structured logging, with request logging middleware
- **API documentation:** OpenAPI document generated by ASP.NET Core, browsed with Scalar
- **CI/CD:** GitHub Actions, building and testing every change and deploying `main` to Azure
- **Hosting:** Azure App Service (Linux) and Azure SQL Database, both on their free tiers, with managed identities instead of passwords
- **Frontend:** Angular and TypeScript (planned)
- **Testing:** xUnit v3 on Microsoft Testing Platform: unit tests for the domain and the use cases (with NSubstitute for the repository and unit of work), and `WebApplicationFactory` with Testcontainers for integration tests

## Architecture decisions

Significant design decisions are recorded as architecture decision records (ADRs) in [`docs/adr`](docs/adr/README.md), using the MADR format. Each one explains the context, the options considered and why one was chosen, for example why the solution uses Clean Architecture, why money is a value object, and why the integration tests use a real SQL Server.

## Domain model

The business rules live in `InvoiceTracker.Domain`, which references no other project or package, so it can't use the database or the web by mistake.

- **`Money`:** an amount and an ISO 4217 currency code. Immutable; adding or subtracting different currencies throws. `Round` rounds to a currency's minor units (its decimal places), with halves away from zero. Stored as `decimal(19,4)`.
- **`Result` and `Error`:** business actions return a `Result` instead of throwing when they're refused. An `Error` has a stable code, such as `Invoice.NotDraft`, a message and a type: validation, not found, conflict or business rule. A validation error also lists the problems for each field. Exceptions are kept for bugs.
- **`Customer`:** created through `Customer.Create`, which requires a name and email. The ID is assigned by the database.
- **`Currency`:** a supported currency: its ISO 4217 code, its minor units and its name. The currencies are rows in a `Currencies` table, seeded by a migration: GBP, EUR, USD and INR for now, all with 2 minor units. Adding one is a new row, not new code.
- **`Invoice`:** an aggregate root with a customer, a currency and its lines. It starts as a draft, and lines can only be added while it's a draft. Issuing needs at least one line and gives the invoice its number and its issue and due dates. Only an issued invoice can be voided. The currency's minor units are copied onto the invoice when it's created, so later changes to the currency don't change it.
- **`InvoiceLine`:** a description, a quantity and a unit price, in the invoice's currency, which is stored once on the invoice. The line total is rounded to the currency's minor units, with halves away from zero, and stored. The invoice total is the sum of the rounded lines, so the lines always add up to it.
- **`InvoiceNumber`:** `INV-<year>-<counter>`, given when the invoice is issued. The counter restarts each year and has at least 4 digits.
- **Repositories:** each aggregate root is loaded and added through its own repository, such as `ICustomerRepository`, built on a generic `IRepository<T>` that only accepts aggregate roots. Changes are saved through `IUnitOfWork`, in one transaction. In Infrastructure, the unit of work is the request's `DbContext`, so whatever a repository adds is saved together. The interfaces live in the Domain; the EF Core implementations live in `InvoiceTracker.Infrastructure`.

The reasons for the money, numbering and currency rules are in ADRs [0009](docs/adr/0009-money-value-object.md), [0017](docs/adr/0017-invoice-numbering.md), [0018](docs/adr/0018-currencies-and-rounding.md) and [0020](docs/adr/0020-currency-once-per-invoice.md).

## Application layer

The use cases live in `InvoiceTracker.Application`. It references the Domain and FluentValidation, but not EF Core or ASP.NET Core, so the same use case can be called from a controller now and from a background worker later.

- **Commands and handlers:** each use case has a command and a plain handler class, such as `CreateCustomerCommand` and `CreateCustomerHandler`, registered in DI and injected into the controller. There is no mediator library.
- **Validation:** each handler runs its FluentValidation validator before touching the domain. If the command is invalid, it returns a validation error with the problems for each field.
- **Queries:** reads skip the repositories. They go through query interfaces such as `ICustomerQueries` and `IInvoiceQueries`, which return response DTOs, and nothing is tracked (`AsNoTracking`). A customer is read with `Select`, so no entity is loaded. An invoice is loaded with its lines and mapped in memory, because its number format and totals are domain code.
- **Reference data:** `CreateInvoiceHandler` checks the currency through `ICurrencyProvider`. The implementation caches the currency list in memory with HybridCache for an hour, so creating an invoice doesn't read the table every time.
- **Errors to HTTP:** the API turns a validation error into a `400` with `ValidationProblemDetails`. The other types become Problem Details with the error's message: not found is `404`, conflict is `409` and a business rule is `422`, such as an invoice for a customer that doesn't exist.

The reasons for each choice are in ADRs [0012](docs/adr/0012-request-validation.md), [0013](docs/adr/0013-plain-command-handlers.md), [0014](docs/adr/0014-query-side.md), [0016](docs/adr/0016-error-to-problem-details.md) and [0019](docs/adr/0019-caching-reference-data.md).

## Running the application

### Prerequisites

- [.NET 10 SDK](https://dotnet.microsoft.com/download) (10.0.402 or later; pinned in `global.json`)
- JetBrains Rider or VS Code
- [Docker Desktop](https://www.docker.com/products/docker-desktop/)
- The EF Core CLI, pinned in `dotnet-tools.json`. Restore it from the repository root with `dotnet tool restore`
- A trusted HTTPS development certificate:

  ```bash
  dotnet dev-certs https --trust
  ```

### Start SQL Server

1. Copy [`.env.example`](.env.example) to `.env` and set a strong `MSSQL_SA_PASSWORD` (at least 8 characters, from three of: upper case, lower case, digits, symbols). `.env` is git-ignored.
2. Start the database defined in [`compose.yaml`](compose.yaml):

   ```bash
   docker compose up -d
   ```

3. Wait until `docker compose ps` shows the container as `healthy`.

To stop it, run `docker compose stop` (start it again with `docker compose start`). `docker compose down` removes the container but keeps the data volume; `docker compose down -v` also deletes the data.

### Configure the connection string

The API reads `ConnectionStrings:InvoiceTrackerDb` from configuration. For local development, store it with the Secret Manager so it never enters the repository:

```bash
dotnet user-secrets set "ConnectionStrings:InvoiceTrackerDb" "Server=localhost,1433;Database=InvoiceTracker;User Id=sa;Password=<your MSSQL_SA_PASSWORD>;TrustServerCertificate=True" --project src/InvoiceTracker.Api
```

### Create the database

```bash
dotnet ef database update --project src/InvoiceTracker.Infrastructure --startup-project src/InvoiceTracker.Api
```

The migrations live in the Infrastructure project, and the API is the startup project that supplies the connection string.

### Run the API

From the repository root:

```bash
dotnet run --project src/InvoiceTracker.Api --launch-profile https
```

Or open `InvoiceTracker.sln` in Rider and select the **InvoiceTracker.Api: https** run configuration.

The API listens on `https://localhost:7160`.

### Authentication

Every `/api` endpoint needs an OAuth 2.0 access token, sent as `Authorization: Bearer <token>`. The API validates the token with ASP.NET Core's JwtBearer handler and reads the caller's app roles from its `roles` claim.

| App role | Allows |
|---|---|
| `InvoiceTracker.Read` | The `GET` endpoints |
| `InvoiceTracker.ReadWrite` | Every endpoint |

- No token, or an invalid or expired one, returns `401` with a `WWW-Authenticate: Bearer` header.
- A valid token without the role the endpoint needs returns `403`.
- The health checks, the OpenAPI document and Scalar need no token.
- A token is required by default, through a fallback policy, so a new endpoint is protected even without an `[Authorize]` attribute.

The reasons for these choices are in [ADR 0021](docs/adr/0021-entra-id-access-tokens-and-app-roles.md).

**Locally**, the API trusts tokens from `dotnet user-jwts`, which comes with the .NET SDK. It signs them with a key kept in user secrets and writes its issuer and audiences to `appsettings.Development.json`. Create one token for each role:

```bash
dotnet user-jwts create --project src/InvoiceTracker.Api --claim roles=InvoiceTracker.Read --valid-for 7d --output token
```

```bash
dotnet user-jwts create --project src/InvoiceTracker.Api --claim roles=InvoiceTracker.ReadWrite --valid-for 7d --output token
```

Use `--claim roles=...`, not `--role`, which writes a different claim name. The API reads `roles`, the claim Entra ID uses.

**In Production**, the API trusts tokens from the Entra ID tenant in [`appsettings.Production.json`](src/InvoiceTracker.Api/appsettings.Production.json): the tenant's v2.0 authority, and the API's client ID as the audience. JwtBearer downloads Entra's signing keys from the authority, so no key is stored. Calling apps get their tokens with the client credentials flow.

### API documentation

In Development, the API publishes an [OpenAPI](https://www.openapis.org) document describing its endpoints and an interactive reference page built from it with [Scalar](https://scalar.com):

| URL | Purpose |
|---|---|
| `https://localhost:7160/openapi/v1.json` | The OpenAPI document, generated from the code. |
| `https://localhost:7160/scalar` | Scalar API reference: browse the endpoints and send test requests. |

Running the API from a launch profile (Rider or `dotnet run`) opens the Scalar page in the browser. Both URLs are only available in Development, so the API surface is not exposed in other environments.

The document describes the bearer token, so Scalar shows an authentication box. Paste a token from `dotnet user-jwts` there to send requests.

### Customers

| Endpoint | Purpose |
|---|---|
| `POST /api/customers` | Creates a customer from a name and an email address. Returns `201` with a `Location` header pointing at the new customer and no body, or `400` with the problems for each field. |
| `GET /api/customers/{id}` | Returns the customer's ID, name and email address, or `404` when there is no customer with that ID. |

For example, posting an empty name and an invalid email address returns:

```json
{
  "type": "https://tools.ietf.org/html/rfc9110#section-15.5.1",
  "title": "One or more validation errors occurred.",
  "status": 400,
  "errors": {
    "Name": ["'Name' must not be empty."],
    "Email": ["'Email' is not a valid email address."]
  },
  "traceId": "00-d6028d342e73878e02727bde878a5146-80f0910a58c63abd-00"
}
```

### Invoices

| Endpoint | Purpose |
|---|---|
| `POST /api/invoices` | Creates a draft invoice from a customer ID, a currency and at least one line, each with a description, quantity and unit price. Returns `201` with a `Location` header pointing at the new invoice and no body, `400` with the problems for each field, or `422` when the customer doesn't exist or the currency isn't supported. |
| `GET /api/invoices/{id}` | Returns the invoice with its status, number, dates, total and lines, or `404` when there is no invoice with that ID. |

The supported currencies are GBP, EUR, USD and INR. Each line total is rounded to the currency's decimal places, with halves away from zero, and the invoice total is the sum of the rounded lines. Quantities and unit prices keep up to 4 decimal places.

For example, a draft in GBP with 4 × 55 and 1 × 0.125 returns:

```json
{
  "id": 1,
  "customerId": 1,
  "number": null,
  "status": "Draft",
  "currency": "GBP",
  "issueDate": null,
  "dueDate": null,
  "total": 220.13,
  "lines": [
    { "description": "Website redesign", "quantity": 4.0000, "unitPrice": 55.0000, "total": 220.00 },
    { "description": "Printing", "quantity": 1.0000, "unitPrice": 0.1250, "total": 0.13 }
  ]
}
```

### Health checks

| Endpoint | Purpose |
|---|---|
| `GET /health/live` | Liveness: the process is running and responding. Runs no dependency checks. |
| `GET /health/ready` | Readiness: the API's dependencies are available. Runs the checks tagged `ready` (currently the SQL Server connection) and returns `503` when the database is unreachable. |

Both return JSON. For example, from `/health/ready`:

```json
{ "status": "Healthy", "checks": [ { "name": "database", "status": "Healthy", "description": null } ] }
```

### Example requests

[`InvoiceTracker.Api.http`](src/InvoiceTracker.Api/InvoiceTracker.Api.http) has a request for each endpoint, including the `401` and `403` cases, written for Rider's HTTP client. It reads the tokens from `http-client.private.env.json` in the same folder, which is git-ignored. Create it with a `dev` environment holding the two tokens:

```json
{
  "dev": {
    "readToken": "<InvoiceTracker.Read token>",
    "writeToken": "<InvoiceTracker.ReadWrite token>"
  }
}
```

Then select `dev` in the environment list at the top of the `.http` file.

### Error responses

Errors are returned as Problem Details ([RFC 9457](https://www.rfc-editor.org/rfc/rfc9457)) with the content type `application/problem+json`, so clients can handle every error the same way.

- **Unhandled exceptions** return `500` with a generic message. Exception details are never sent to clients outside Development.
- **Empty error responses**, such as a `401`, a `403` or a `404` for an unknown route, get a Problem Details body.
- **Development** still shows the full exception details, as Problem Details for API clients (or as an HTML page in a browser).

For example, a request with a token to an unknown route returns the response below. Without a token, the same request returns `401`, because the fallback policy also covers routes that don't exist.

```json
{
  "type": "https://tools.ietf.org/html/rfc9110#section-15.5.5",
  "title": "Not Found",
  "status": 404,
  "traceId": "00-98018a5a63bf32ac72605b6df3c1d7a9-cc6a721fa3f06d60-00"
}
```

The `traceId` identifies the request. Its middle part (32 characters) is the trace ID that appears at the end of the matching log lines, so an error a client reports can be traced in the logs.

### Logging

The API logs with Serilog. Levels and outputs are set in the `Serilog` section of [`appsettings.json`](src/InvoiceTracker.Api/appsettings.json), not in code, so they can change per environment without a rebuild.

- **Console:** in every environment.
- **File:** in Development only ([`appsettings.Development.json`](src/InvoiceTracker.Api/appsettings.Development.json)), a daily rolling file named `logs/log-yyyyMMdd.txt` in the working directory (the project folder when run from Rider). Files are kept for 14 days, up to 31 files. The `logs` folder is git-ignored.
- **Requests:** each HTTP request is written as one structured event with the method, path, status code and elapsed time. `5xx` responses are logged as errors. The framework's own per-request logs are reduced by setting `Microsoft.AspNetCore` to `Warning`.
- **Startup:** a console-only bootstrap logger runs before configuration loads, so a failed startup is still logged.
- **Format:** console and file lines use a Serilog.Expressions `ExpressionTemplate`, configured in the same `appsettings` files. Output is plain text, without colours, so it reads the same on light and dark backgrounds.
- **Caller:** when a request has a token, its log line also shows `caller=`, the token's `oid` claim (the user or app that called), and `client=`, its `azp` claim (the client ID of the calling app). Requests without a token leave both out.
- **Trace ID:** each line written during a request ends with the request's trace ID in brackets, matching the `traceId` in error responses. Lines written outside a request, such as at startup, have no trace ID and end after the message.

Example output:

```
[2026-11-08 13:48:02 Info] Hosting environment: Development
[2026-11-08 13:48:10 Info] HTTP GET /health/live responded 200 in 5.6788 ms (6b8b592374673259511a6f1f12a42cf1)
[2026-11-08 13:48:19 Info] HTTP GET /api/customers/1 responded 200 in 37.3220 ms caller=11111111-1111-1111-1111-111111111111 client=22222222-2222-2222-2222-222222222222 (f569ca3a44fe175002e5d96cb9ae6791)
```

To change a level without editing a file, override the configuration key with an environment variable, for example `Serilog__MinimumLevel__Default=Debug`.

### Run the tests

With Docker Desktop running, from the repository root:

```bash
dotnet test --solution InvoiceTracker.sln
```

Or run them from the test runner in Rider.

The domain and application unit tests need no Docker or database and run in about a second. To run only those:

```bash
dotnet test --project tests/InvoiceTracker.Domain.UnitTests
```

```bash
dotnet test --project tests/InvoiceTracker.Application.UnitTests
```

The integration tests do not use the Compose database or the connection string above. Each run starts one SQL Server container with Testcontainers and one in-memory instance of the API with `WebApplicationFactory`, shared by all test classes through an xUnit assembly fixture, and removes the container afterwards. The fixture applies the EF Core migrations when it starts, so the test database has the same schema as the real one. The first run is slower while the SQL Server image downloads.

The integration tests sign their own access tokens with a random key, created for each run, and the API trusts that key during the tests. They cover a missing, invalid, expired or wrongly addressed token, a missing role and a valid one, without calling Entra ID.

## Continuous integration (CI)

Every pull request to `main`, and every push to `main`, runs the [CI workflow](.github/workflows/ci.yml) on GitHub Actions. It restores, builds and tests the solution in Release, using the SDK pinned in `global.json`. The integration tests start SQL Server in Docker on the GitHub Actions runner. Pull requests can only be merged once the `build` check passes.

The workflow is based on GitHub's official [.NET starter workflow](https://github.com/actions/starter-workflows/blob/main/ci/dotnet.yml). I updated the action versions, read the SDK version from `global.json`, and added read-only permissions and cancellation of outdated runs.

Every action in both workflows is pinned to a full commit SHA, with its version in a comment, so a tag moved upstream can't change what runs. [Dependabot](.github/dependabot.yml) checks for new versions every week and opens a pull request to update the pins.

Runs are listed under the repository's [Actions tab](https://github.com/ankitroykr/invoice-payment-tracker/actions).

## Continuous deployment (CD)

When CI passes on a push to `main`, the [deploy workflow](.github/workflows/deploy.yml) releases that commit to Azure. It can also be started by hand from the Actions tab.

1. Publishes the API and builds an EF Core migration bundle.
2. Signs in to Azure with OpenID Connect as a user-assigned managed identity. Azure trusts it only for this repository's `production` environment, which only `main` can deploy to, so no password or publish profile is stored in GitHub.
3. Opens the SQL firewall to the runner's IP address, applies the migrations, and removes the rule again, even if a step fails.
4. Deploys the API to App Service, then checks `/health/ready` on the live app.

In Azure, the API runs on App Service Free (F1) on Linux, with an Azure SQL Database on the free offer, set to pause rather than bill if the monthly allowance runs out.

- **No passwords:** the app signs in to SQL with its own managed identity, through `Authentication=Active Directory Managed Identity` in its connection string. The SQL server only accepts Microsoft Entra sign-ins.
- **Least privilege:** the app's database user can read and write rows but not change tables. Only the deploy identity can change tables, and only during a deploy.
- **Network:** the SQL firewall only allows the app's possible outbound IP addresses, not just the ones in use now, because App Service can switch between them. F1 has no virtual network integration.
- **Settings:** Production reads the Entra ID settings from [`appsettings.Production.json`](src/InvoiceTracker.Api/appsettings.Production.json). The connection string is set on the App Service, not in the repository.
- **Free tier limits:** the first request after a quiet spell is slow, while the app starts and the database resumes.

The reasons for these choices are in [ADR 0022](docs/adr/0022-host-on-azure-free-tiers.md).
